# 3D-тур по школе на Unreal Engine 5 (UE 5.5)

Интерактивный фотореалистичный 3D-тур по зданию школы, реализованный на **Unreal Engine 5.5**. Проект обеспечивает свободное перемещение пользователя внутри виртуальной модели, навигацию по ключевым зонам и демонстрирует инженерно-обоснованный подход к созданию образовательной цифровой среды: от модульного моделирования и PBR-материалов до оптимизации производительности, процедурной погодной системы и ролевого разграничения доступа (RBAC).

## 1. Введение и актуальность

Современное образование всё чаще использует цифровые среды как инструмент повышения доступности информации, качества визуализации и эффективности коммуникации. Виртуальные 3D-пространства позволяют:
- проводить предварительное знакомство с объектом без физического присутствия;
- снижать барьеры адаптации (особенно для новых учащихся);
- поддерживать навигацию и логистику внутри здания;
- формировать интерактивные учебные материалы и экскурсионные сценарии.

В качестве технологической базы выбран **Unreal Engine 5** — движок, обеспечивающий фотореалистичную графику и интерактивность. В рамках проекта создана виртуальная модель школьного здания, позволяющая пользователю свободно перемещаться по пространству и изучать доступные локации.

## 2. Цель, задачи, объект и предмет

### Цель
Создание **3D-модели основных помещений здания школы** и реализация **виртуального перемещения пользователя** внутри модели для:
- удобного поиска нужного кабинета/локации;
- удалённого просмотра помещений, доступных посетителям.

### Задачи
1. **Исследование и анализ**
   - изучить структуру и архитектуру здания;
   - выделить приоритетные зоны (классы, актовый зал, спортзал, столовая и т.д.).
2. **Разработка 3D-модели**
   - создать высокодетализированную модель здания;
   - реализовать материалы и освещение, обеспечивающие визуальную достоверность.
3. **Интеграция управления**
   - реализовать управление перемещением и обзором в UE5;
   - создать понятный интерфейс взаимодействия.
4. **Тестирование и оптимизация**
   - выявить и устранить ошибки;
   - обеспечить стабильную производительность на целевых устройствах.
5. **Оценка пользовательского опыта**
   - пилотное тестирование среди учащихся/сотрудников;
   - анализ обратной связи и улучшения.
6. **Внедрение и масштабирование**
   - подготовить основу для методических рекомендаций;
   - предусмотреть меры безопасности и разграничение доступа.

### Объект и предмет
- **Объект:** школьное здание (типовое; в работе использованы данные Школы №1155).
- **Предмет:** методика создания интерактивной фотореалистичной 3D-среды на UE5 и её инженерная оптимизация.

## 4. Методика выполнения работы

### 4.1. Сбор исходных данных и масштабирование

Для воспроизведения геометрии и пропорций использовались:
- схемы/планы здания;
- фотоматериалы из открытых источников (для анализа фасадов, оконных модулей, цветовых решений).

Критически важный этап — **приведение сцены к корректному масштабу**, так как любая ошибка в метрике приводит к:
- неверному восприятию пространства пользователем;
- проблемам коллизий и передвижения;
- некорректной работе освещения и отражений.

Изначально выявленные неточности размеров стали основанием для переноса и уточнения макета в Blender с последующей сборкой в UE5.

---

### 4.2. Модульная 3D-модель (3×3×3 м) и сборка здания

Ключевым инженерным решением проекта является **модульный принцип построения**:
- базовая ячейка: **3×3×3 метра**;
- модули включают повторяющиеся элементы: стены, окна, проёмы, перекрытия.

Почему это важно (проектная мотивация):
1. **Точность воспроизведения**: повторяемые элементы легче выверять по референсам.
2. **Скорость сборки**: здание конструируется как “конструктор” из согласованных блоков.
3. **Масштабируемость**: метод применим к другим типовым зданиям без пересборки с нуля.
4. **Оптимизация**: модульность упрощает управление LOD/HLOD и стримингом.

Пример модуля — примитивная сборка из:
- пола/перекрытия,
- оконной рамы,
- стеклопакета.

Далее из модулей формируется каркас здания: этажность, внутренние объёмы, проёмы, связи помещений.

---

### 4.3. Материалы и визуальная достоверность (PBR)

Визуальная правдоподобность обеспечивается через PBR-подход:
- материалы описываются физически интерпретируемыми параметрами (base color, roughness, metalness, normal и т.д.);
- реакция на освещение и отражения согласована с глобальным светом сцены.

В рамках проекта подготовлены базовые материалы:
- **WallBrick Material** — белый бетон/стена с шероховатостью для глубины и читаемости фактуры;
- **Glass Material** — универсальный материал стекла с параметрами:
  - прозрачность,
  - оттенок,
  - “кривизна/искажение” (как художественно-физическая имитация),
  - производные варианты (в т.ч. эффекты типа “разбитое/резное стекло” как расширение набора).

Практическая цель материалов — обеспечить узнаваемость объекта и устойчивую читаемость архитектуры при разных условиях освещения и погоды.

---

### 4.4. Реализация 3D-тура: перемещение и режимы камеры

Проект включает систему перемещения с двумя режимами обзора:

#### First-Person Mode (первое лицо)
- используется базовый контроллер **FirstPersonCharacter**, адаптированный под требования проекта;
- физика движения — **UCharacterMovementComponent**;
- движение — через `AddMovementInput()` (направление на основе вектора ввода);
- камера — **UCameraComponent**, закреплённая для симуляции взгляда человека.

#### Third-Person Mode (третье лицо)
- используется **ThirdPersonCharacter**;
- камера установлена через **USpringArmComponent**:
  - обеспечивает устойчивое следование камеры за персонажем,
  - сглаживает движение и повороты,
  - контролирует дистанцию до персонажа;
- поворот обзора — через `AddControllerYawInput()` (управление углом).

#### Дополнительные механики
- прыжок: `LaunchCharacter()` (корректное ускорение по оси Z);
- сглаживание: `FMath::VInterpTo()` и `FMath::RInterpTo()` для интерполяции позиции и поворотов;
- бег: изменение скорости при удержании модификатора (например, Shift).

**Верификация корректности** включала:
- тест коллизий и проходимости,
- контроль “застреваний” и конфликтов с геометрией,
- контроль плавности и стабильности кадров.

---

### 4.5. Интерактивность и UI-навигация

#### Взаимодействие с объектами
Для интерактива использован трассировочный подход:
- `LineTraceByChannel()` определяет объект перед игроком;
- логика взаимодействия применяется к интерактивным объектам (двери, стенды и др. — расширяемо).

#### UI и навигация
- интерфейс реализован на **UMG**:
  - меню,
  - настройки,
  - элементы навигации;
- добавлена **мини-карта** для повышения ориентирования и “читаемости” пространства.

## 5. Оптимизация производительности и качества

Оптимизация рассматривалась как равноправная часть разработки: фотореализм должен сочетаться со стабильной частотой кадров при реальном использовании.

### 5.1. Nanite и Lumen

- **Nanite**
  - автоматическое управление микрополигональной сеткой;
  - позволяет использовать высокодетализированные модели без ручного создания LOD-цепочек;
  - снижает трудоёмкость подготовки ассетов и повышает визуальную стабильность.

- **Lumen**
  - глобальное освещение в реальном времени (GI);
  - корректные отражения, в т.ч. на стеклянных поверхностях;
  - исключение необходимости запекания lightmaps в большинстве сценариев.

Цель: максимальная визуальная достоверность при контролируемой стоимости рендера.

---

### 5.2. World Partition и HLOD

Для сцены внедрены:
- **World Partition** — разбиение мира на стриминговые ячейки;
- **HLOD** — иерархические уровни детализации для удалённых объектов.

Инженерный эффект:
- при удалении пользователя от зоны часть акторов выгружается/упрощается;
- уменьшается нагрузка на CPU/GPU;
- повышается стабильность кадровой частоты в длительных сессиях.

---

### 5.3. Оптимизация растительности

Снижение FPS после добавления Foliage — типичная проблема реалтайм-визуализации. В проекте применены меры:
- переход на **Hierarchical Instanced Static Mesh** (HISM) для массовых объектов;
- настройка **Cull Distance Volume** для деревьев/травы (контролируемое отсечение по расстоянию);
- оптимизация теней (уменьшение каскадов при сохранении качества ближнего каскада);
- использование **Virtual Shadow Maps** для устойчивых динамических теней.

## 6. Динамическое небо и погода (Ultra Dynamic Sky / Weather)

### 6.1. Цели и методологические основания

Подсистема атмосферы проектировалась как:
- **правдоподобная** (визуально реалистичная),
- **устойчивая** (без резких скачков яркости и экспозиции),
- **контролируемая** (с управляемым бюджетом производительности),
- **расширяемая** (под сценарии экскурсии и демонстрации).

Методологический принцип: процедурная параметризация вместо статичных текстур. Управляемые параметры:
- время суток,
- облачность,
- туман/оптическая толща,
- осадки,
- ветер.

Ключевые требования:
- согласованность с Lumen GI и тенями,
- непрерывность переходов,
- отсутствие деградации при многократных переключениях профилей.

---

### 6.2. Архитектура и алгоритмы

Подсистема основана на Ultra Dynamic Sky / Weather и компонентах UE5:
- **SkyAtmosphere** — модель рассеяния (Рэлея/Ми);
- **Volumetric Cloud** — процедурные облака;
- **Directional Light (Sun/Moon)** — главный источник света;
- **SkyLight** — окружение и отражения (возможен периодический recapture);
- **Exponential Height Fog + Volumetric Fog** — воздушная перспектива и градиент дымки;
- **WindDirectionalSource** — синхронизация ветра (атмосфера ↔ растительность);
- **Niagara (GPU)** — осадки (дождь/снег/град) с дистанционным LOD;
- исключающие объёмы/ограничения для интерьеров (чтобы осадки не “проникали” внутрь).

Управление сведено к актору-оркестратору (менеджеру погоды), который:
- хранит **профили погоды** (ясно/облачно/туман/дождь/снег/гроза);
- выполняет **плавные переходы** (через Timeline/кривые) по ключевым параметрам:
  - интенсивность света и цветовая температура,
  - плотность тумана,
  - покрытость облаков,
  - сила ветра,
  - интенсивность осадков.

Для стабилизации яркости применяется автоэкспозиция в режиме гистограммы с ограничением коридора (чтобы переходы не создавали “выстрелы” яркости).

Производительность обеспечивается:
- ограниченным каденсом обновлений “дорогих” компонентов (например, recapture),
- фиксированными объёмами симуляции Niagara,
- дистанционным прореживанием частиц,
- согласованием с World Partition/HLOD (подсистема не должна разрушать стриминг-логики).

## 7. Аутентификация и разграничение доступа (RBAC)

### 7.1. Цели и требования

В проект встроена ролево-ориентированная модель доступа (**RBAC**) для дифференциации прав просмотра и интерактивности. Роли:
- `Guest` — минимальные права,
- `Parent` — частичный доступ,
- `Student` — полный доступ к учебным зонам.

Требования:
- автономная работа (offline, без обязательного сервера),
- отсутствие хранения паролей в открытом виде,
- автологин при повторном запуске,
- архитектурная готовность к будущему серверному сценарию,
- корректный UX: единая форма входа и мягкая блокировка недоступного контента.

---

### 7.2. Архитектура и алгоритм

Архитектура состоит из четырёх компонент:

1) **Данные**
- структура `S_AccountData`:
  - `Username: String`
  - `AccessLevel: E_AccessLevel`
  - `HashedKey: String`
- список аккаунтов встроен в клиент и хранится в `BP_AccessManager`
- роли представлены перечислением:
  - `E_AccessLevel { Guest, Parent, Student }`

2) **Проверка доступа**
- виджет `WBP_LoginPanel` принимает ввод,
- формирует строку `Input + Salt`,
- вычисляет `SHA-256`,
- вызывает `BP_AccessManager.CheckAccessByHash(HashedInput)`:
  - возвращает валидность, имя, роль.

Важно: UI не читает “сырые” данные аккаунтов напрямую — только через публичный API менеджера.

3) **Персистентность (SaveGame)**
- `SG_UserAccess`:
  - `CanUseGame: Bool`
  - `Username: String`
  - `AccessLevel: E_AccessLevel`
- сохранение в слот `UserAccessSlot`
- при запуске:
  - если слот существует и `CanUseGame=true` → вход без показа формы
- кнопка “Сменить пользователя” удаляет/обнуляет слот и возвращает к форме.

4) **Интеграция с контентом**
- интерактивы/двери/пункты UI проверяют роль:
  - скрывают элементы,
  - запрещают действия,
  - ограничивают доступ к зонам.

**Поток выполнения:**
`Launch → DoesSaveGameExist(UserAccessSlot) → Load → CanUseGame? → ApplyRole → Enter`
или
`Launch → Login UI → Hash(Input+Salt) → CheckAccessByHash → SaveGame → Enter`.

### 7.3. Защита, устойчивость и расширяемость

**Защита:**
- в сборке хранятся только **хэши** ключей, а не исходные пароли;
- добавление соли снижает риск атак по предвычисленным таблицам;
- введённые ключи не сохраняются в SaveGame и не логируются.

**Устойчивость:**
- поиск совпадений реализован с корректной обработкой отсутствия совпадений;
- предусмотрены проверки пустых коллекций;
- исключены рекурсивные сценарии и потенциальные бесконечные циклы.

**Расширяемость:**
- предусмотрена возможность подключить серверный сценарий (например, получение JSON-аккаунтов),
  при этом клиентская логика UI и проверки прав сохраняется.

## 8. Запуск проекта

> **Важно про UE-репозитории:** проекты Unreal содержат большие бинарные ассеты. Для GitHub рекомендуется **Git LFS** и грамотное разделение: исходники/конфиги в репо, тяжёлые ассеты — через LFS или релизы.

### Требования
- **Unreal Engine 5.5**
- **Blender 4.3.2** (не обязателен для запуска, нужен для редактирования моделей)
- Плагины/ассеты (если используются из Marketplace):
  - Ultra Dynamic Sky
  - Ultra Dynamic Weather  
  *(уточнение: Marketplace-контент часто нельзя свободно распространять в публичном репозитории; корректный путь — установка через Launcher пользователем).*

### Быстрый старт
1. Установить **UE 5.5**.
2. Открыть `.uproject` файл проекта.
3. Дождаться компиляции (если есть C++ модуль) и сборки шейдеров.
4. Запуск:
   - из редактора: **Play**
   - или собрать packaged build (Windows) через **Package Project**.
